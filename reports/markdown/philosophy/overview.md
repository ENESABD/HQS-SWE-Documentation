This guide is structured to reflect how we think about building quality software — starting with values, then people, then practices, and finally tools.

## The Structure

**Philosophy** — What software engineering is, what success means, and the values that guide us. This is the foundation.

**Collaboration** — How people work together. We cover this before technical topics because no amount of good code can save a dysfunctional team.

**Practices** — How we work day-to-day. TDD, pair programming, continuous integration — the habits that enable quality.

**Design** — How we think about code structure. Principles and patterns that emerge from practice and guide refactoring.

**Technologies** — What we build with. Frameworks, languages, and tools — understood as solutions to developer problems.

**Example** — A real project that demonstrates these ideas in practice.

## Why This Order

The order is intentional:

1. **Values before methods** — Without understanding _why_, the _how_ becomes dogma
2. **People before code** — Technical excellence means nothing if the team can't collaborate
3. **Practices before design** — Good design emerges from working code and refactoring, not upfront planning
4. **Design before technologies** — Principles are stable; tools change constantly
5. **Example last** — Theory is easier to see once you have concrete examples

You don't have to read linearly. Jump to what you need. But if you're starting fresh, this order tells a coherent story.
